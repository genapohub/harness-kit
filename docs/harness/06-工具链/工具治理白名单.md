# 工具治理白名单 · 角色分级治理（v1.1）

> Harness L3 约束层（最小特权原则）的具体落地。
> 每个角色 SKILL.md 末尾必须挂一份「禁止调用工具清单」，本文件统一汇总 + 提供模板。
> **原则**：白名单以外的工具调用必须先问人类，得到明确许可才能用。
> **v1.1 变更**：13+1 角色按「激活分级」重排为 P0/P1/P2 三档。未激活角色不参与维护；激活前必须 refresh。

---

## 一、总则

### 1.1 工具分级

| 级别 | 类型 | 调用要求 |
|---|---|---|
| **L1 只读** | Read / Glob / Grep / WebFetch / WebSearch | 默认允许 |
| **L2 写入** | Write / Edit / Bash（非破坏性） | 需在对的工作目录 + 有 git 跟踪 |
| **L3 破坏性** | rm / mv / chmod / dd / mkfs | **必须人类批准** |
| **L4 外发** | curl POST / 邮件 / 推送消息 | **必须人类批准 + 脱敏** |
| **L5 远程执行** | ssh / kubectl / ansible | **禁止（除非显式授权）** |

### 1.2 红线（所有角色通用，与分级无关）

```
❌ 禁止调用任何破坏性命令到生产环境数据库
❌ 禁止外发客户代码/合同/财务数据到公网模型
❌ 禁止修改 CI/CD 配置（.github/workflows / .gitlab-ci.yml）
❌ 禁止直接 push 到 main/master 分支
❌ 禁止 rm -rf / mkfs / dd if=/dev/zero 等无差别破坏
❌ 禁止 ssh 到生产服务器执行写操作
❌ 禁止在 commit message / PR 描述里泄露密钥
❌ 禁止替人类做架构决策（架构变更需人类拍板）
```

### 1.3 激活分级规则（v1.1 新增）

| 档位 | 含义 | 维护要求 |
|---|---|---|
| **P0 常驻**（6 个） | 每个软件项目装机即激活（开发-测试-部署闭环） | 完整维护：边界表 + 季度复盘 + evals scope |
| **P1 阶段激活**（3 个） | 项目进入对应阶段才拉起 | 边界表保留，复盘降为半年一次 |
| **P2 挂起**（6 个） | 当前项目类型用不到 | 条目保留仅作参考，**不参与季度复盘**；激活前必须 refresh |

**配套规则**：

1. **项目激活集以项目 AGENTS.md「激活角色清单」为准**（模板见 `02-规范/AGENTS.md` 第二部分），本文件的分级是默认建议，不替代项目勾选。
2. **分级是动态的**：角色提级/降级属于本文件变更，需更新版本号并打 `harness-vX.Y` tag。
3. **P2 激活前必须 refresh**：挂起期间工具链、MCP、工作区结构可能已变化，激活时先按模板重走一遍该角色的边界确认，再改档位。

### 1.4 边界表模板（每个角色复制本段到 SKILL.md 末尾）

```markdown
## 【本角色】工具治理白名单

### 允许调用（L1 只读）
- Read / Glob / Grep
- 【角色专属工具】

### 可调用但需谨慎（L2 写入）
- Write / Edit（仅限本职责范围的文件）
- Bash（仅限非破坏性命令）

### 禁止调用
- 【角色禁止项】

### 红线场景
- 【本角色特有的越权场景】
```

## 二、P0 常驻角色（6 个 · 完整维护）

### 2.1 tech-lead-guide（技术负责人 / 架构师）

**允许**：
- L1 全部只读工具
- 所有 L2 写入（但需在文档中标注决策依据）
- WebSearch / WebFetch（技术调研）

**禁止**：
- 替业务方做产品决策（这是产品经理的活）
- 直接执行跨角色大规模改动（必须先 orchestrator 调度）

**红线**：架构决策变更必须留 ADR（Architecture Decision Record），不许只改代码不留痕。

---

### 2.2 frontend-dev-guide（前端开发）

**允许**：
- L1 全部只读工具
- Write / Edit（前端代码、组件、样式）
- npm install / yarn add（锁版本）
- npm run dev / build / test
- 浏览器自动化（Playwright/Chrome DevTools MCP）

**禁止**：
- 写后端代码（API/数据库）
- 改后端配置文件（nginx.conf / .env）
- 直接部署到生产（npm run deploy 需人类批准）

**红线**：组件库升级必须人类批准，不许 AI 自主 bump major version。

---

### 2.3 backend-dev-guide（后端开发）

**允许**：
- L1 全部只读工具
- Write / Edit（API 代码、数据库迁移、测试）
- pip install -r requirements.txt（锁版本）
- pytest / npm test（本地跑测试）
- Docker build（不部署）

**禁止**：
- 改前端代码（除非是联调必须的 mock）
- 直接连生产数据库（开发库可以）
- 改 nginx / k8s / terraform 配置

**红线**：数据库迁移必须人类审核 + 备份，AI 不许自主 DROP TABLE。

---

### 2.4 qa-testing-guide（测试 / QA）

**允许**：
- L1 全部只读工具
- Write / Edit（测试代码、测试用例）
- 浏览器自动化（Playwright）
- 跑测试（pytest / npm test）
- 提 bug（写到 issue tracker）

**禁止**：
- 改产品代码（除非是测试必须的辅助函数）
- 直接 close bug（必须人类产品审核）
- 跳测试用例（不许用 skip 绕过）

**红线**：测试覆盖率下降的 PR 必须 reject，AI 不许降低覆盖率。

---

### 2.5 devops-guide（DevOps / 运维）

**允许**：
- L1 全部只读工具
- L3 破坏性（在测试环境，AI 可执行 rm / chmod 等，需记录）
- Docker / kubectl（仅限 staging 环境）
- Terraform plan（apply 必须人类批准）

**禁止**：
- 直接 apply 到生产 Terraform
- 直接 kubectl apply 到生产集群
- 直接 rm 生产服务器文件

**红线**：生产环境任何写操作必须人类授权 + 第二人复核。

---

### 2.6 team-orchestrator（调度官）

**允许**：
- L1 全部只读工具
- Write / Edit（调度日志、决策记录）
- 调用其他 13 个角色 SKILL.md（语义匹配 + 触发）

**禁止**：
- 写代码 / 改代码（这是执行角色的活）
- 直接对外发送消息
- 单次调度超过 5 个角色（必须人类拆分）

**红线**：调度决策必须可回溯（写入 project-tracker 决策日志），不许黑盒调度。

## 三、P1 阶段激活角色（3 个 · 按项目阶段拉起）

### 3.1 product-plan-guide（产品经理 · 需求/迭代入口）

**允许**：
- L1 全部只读工具
- Write / Edit（PRD/BRD/MRD 等文档文件）
- WebSearch / WebFetch（行业调研）

**禁止**：
- 写代码（前端/后端/数据库）
- 调用开发工具链（git push / npm install / docker）
- 直接对外发送消息（邮件/IM/推送）

**红线**：PRD 完成后必须人类审核签字，不许 AI 自签。

**激活时机**：新需求立项、版本迭代出 PRD、预研可行性分析。

---

### 3.2 ui-designer-guide（UI/UX 设计师 · 方案/视觉执行/UI 改版/走查）

**允许**：
- L1 全部只读工具
- Write / Edit（设计规范文档、交互文档）
- 设计工具 MCP（MasterGo/Figma/墨刀）

**禁止**：
- 写后端代码 / 数据库 schema
- 直接调用部署工具（Vercel/Netlify/Cloudflare）
- 修改生产环境设计资源

**红线**：UI 走查必须人类设计师审核，AI 不许自评设计。

**激活时机**：UI 改版、设计系统升级、体验走查。

---

### 3.3 data-analyst-guide（数据分析师 · 埋点/指标分析）

**允许**：
- L1 全部只读工具
- SQL 查询（开发库/只读副本）
- Python 数据处理（pandas/numpy）
- BI 工具 MCP（Tableau/帆软/九数云）

**禁止**：
- 写产品代码
- 写 ETL 到生产库
- 跑长时间大查询（>10 分钟）不告知

**红线**：分析报告里的结论必须基于真实数据，AI 不许编造数字。

**激活时机**：埋点方案设计、上线后指标归因、数据体系建设。

## 五、跨角色协作规则

### 5.1 角色接力

当一个角色完成任务需要交接给另一个角色时：

```
交接方（例：product-plan-guide）必须：
  1. 在 project-tracker.md「AI 协作上下文」段更新状态
  2. 列出产出物路径 + 关键决策
  3. 明确下一角色要做什么

接力方（例：frontend-dev-guide）必须：
  1. 先读 project-tracker.md「AI 协作上下文」段
  2. 先读交接方的产出物
  3. 不重复做交接方已完成的工作
```

### 5.2 角色冲突

两个角色对同一文件有不同意见时：

```
1. 先在 project-tracker.md 写决策冲突记录
2. 升级到 tech-lead-guide 做技术决策
3. 涉及业务优先级升级到 product-plan-guide
4. 最终决策由人类拍板
```

### 5.3 与未激活角色的关系（v1.1 新增）

- 项目 AGENTS.md 未勾选的角色，orchestrator **不得调度**（不在本项目激活集 = 不存在）
- 任务确实需要未激活角色时：先由人类确认 → 在项目 AGENTS.md 激活清单中补勾 → 该角色按本文件对应档位边界工作

## 六、维护规则

1. **每个激活角色 SKILL.md 末尾挂一份本表对应段**（不挂视为越权）；P2 挂起角色暂不要求挂载
2. **新增工具/MCP 必须更新本表**（不在白名单 = 默认禁止）
3. **P0 季度复盘一次，P1 半年一次，P2 不复盘**（根据实际越权事件调整边界）
4. **越权事件必须写事故复盘**（写入 05-实战/事故记录.md）
5. **档位调整（提级/降级）必须更新版本号 + 打 `harness-vX.Y` tag**
