# 项目管理方案产出指南

## Overview

本技能将项目管理领域的方法论转化为可执行的工作流。当用户提出项目管理相关需求时，先识别该需求属于 5 类场景中的哪一类，再按对应场景的产出清单生成完整方案——从项目章程到上线检查清单，覆盖项目管理的核心场景。

详细的方法论、各场景产出清单、风险矩阵、会议节奏建议、DoD模板、上线检查清单、质量检查清单均存放在 `references/项目管理方法论.md`，在执行前必须读取对应章节。

## 触发条件

- 用户需要启动新项目、做立项规划
- 用户需要做迭代规划、Sprint计划
- 用户需要做风险评估、风险应对方案
- 用户需要做项目复盘、流程优化
- 用户提到"项目管理""迭代规划""里程碑""WBS""风险""Sprint""进度跟踪""复盘""敏捷"等关键词

## 记忆系统

本技能的完整记忆管理规则（写日志/轮转归档/自清理）定义在 `references/记忆规则.md`，执行前必须读取。

- **执行前（必须）**：读取 `references/记忆规则.md` 中的 Step 0 加载规范 + `.skills-memory/MEMORY.md` 本技能对应分段 + `.skills-memory/YYYY-MM-DD.md`（今日日志，如存在）
- **执行后（硬性要求，不可跳过）**：追加 `[project-mgmt-guide] 场景描述 → 关键决策` 到 `.skills-memory/YYYY-MM-DD.md`；如有可复用决策，去重后追加到 MEMORY.md 对应分段。**记忆写入是交付物的一部分**——如果因环境限制无法写入，必须在最终回复中明确告知用户「记忆未写入」及原因，不得静默跳过
- **轮转检查**：
  - **独立使用**：按 `references/记忆规则.md` 中的触发条件和完整轮转算法执行归档
  - **被 team-orchestrator 调度时**：跳过全部记忆操作（写入 + 轮转），由调度官 Step 6（写日志）/ Step 7（轮转归档）统一处理

## 执行流程

按以下 5 步顺序执行，不可跳步。

### Step 1: 需求理解

- 解析用户输入的项目管理需求
- 提取关键信息：项目类型与规模、团队结构、管理框架(Scrum/Kanban/瀑布/混合)、时间线、关键约束
- 主动提问补全缺失信息（一次最多 2-3 个问题）

### Step 2: 场景识别

读取 `references/项目管理方法论.md` 的"一、场景识别"章节：

| 场景 | 名称 | 判断条件 | 产出量 |
|------|------|---------|--------|
| 场景一 | 0→1 项目启动 | 全新项目、需从立项开始 | 10-12类 |
| 场景二 | 中型迭代/版本规划 | 已有项目版本迭代、多团队 | 6-8类 |
| 场景三 | 小调整/问题跟进 | 单事项跟进、资源微调 | 2-3类 |
| 场景四 | 项目重启/重大调整 | 范围大幅变更、组织调整 | 8-10类 |
| 场景五 | 敏捷转型/流程优化 | 流程改进、敏捷成熟度提升 | 3-4类 |

### Step 3: 与用户确认场景

输出场景判断、判断依据、产出清单、预估周期，确认后进入产出。

### Step 4: 按清单产出方案

读取 `references/项目管理方法论.md` 对应场景章节。

> **专家蒸馏增量（2026-09-06 并入）**：项目由 **AI/多角色协作执行**（orchestrator 调度 / 虚拟团队 / 8 人专家团式编排）时，读取 `references/expert-distill/mvp-team-lead-蒸馏.md`——6 Phase 门禁治理（需求澄清→并行调研→Spec→设计→开发→测试交付）、Spec 即契约 13 章节（范围锁定+版本锚定+EARS 验收+不做清单）、变更分级流程、冲突解决协议、团队 P0 三禁（emoji 图标/紫粉渐变/AI 模板味）。真人敏捷/瀑布项目用原生方法论。需求确认后拆任务阶段，另读取 `references/expert-distill/senior-pm-蒸馏.md`（关德豪：Spec→任务拆解 30-60 分钟粒度 + 每条验收标准 / 去镀金范围纪律 / AI 写任务清单防坑五条）——任务可执行、范围不膨胀。

产出要求：
- 项目目标使用 SMART 原则（具体/可衡量/可达成/相关/有时限）
- WBS粒度控制在每个任务 2-5 天
- 风险登记册含概率×影响矩阵 + 应对策略 + 责任人
- 排期图含关键路径标注 + 依赖关系
- DoD 和上线检查清单使用模板格式
- 遵循"七、项目管理通用规范"
- **必须读取并应用"十一、超越AI味"章节**：产出方案时融入真实岗位经验，拒绝模板化输出
- **优先使用可填空模板**：方法论通用规范章节末尾的「### XX模板（可填空）」，直接按占位符填充（无对应模板则按清单产出）
- 产出后保存为 Markdown 文件

### Step 5: 质量检查

读取 `references/项目管理方法论.md` 的"十、产出质量检查清单"：

- 项目目标与范围清晰（In/Out）
- WBS粒度合理（2-5天/任务）
- 里程碑有交付物+验收标准
- 风险登记册完整
- 沟通计划覆盖所有干系人
- DoD定义明确可执行
- 上线检查清单完整

- **去AI味**：对照"十一、超越AI味"逐条自检，拒绝模板化产出
- 记忆已写入（`.skills-memory/YYYY-MM-DD.md` 有本次会话条目，无则立即补写）

## 注意事项

- 不要跳过 Step 3 的用户确认
- 项目范围必须有明确的 In/Out 边界，不能说"大概这些"
- 风险登记册不能只列风险不列应对，每个风险必须有缓解措施+责任人
- 里程碑必须有可验证的交付物和验收标准
- DoD 不能是形式主义——要具体、可执行、团队达成共识
- 场景四（项目重启）的知识交接方案是硬性要求

## 岗位职责与产出标准（业界锚点 · 2026-08 学习）

**现实岗位职责**：①全流程管理——立项/规划/执行/监控/收尾五阶段；②范围与计划——WBS 分解、甘特图、关键路径；③进度追踪纠偏——识别偏差（SV/CV）、赶工/快速跟进；④资源协调与冲突解决；⑤风险管理——识别/评估（高中低分级）/应对（规避/转移/减轻/接受）；⑥沟通汇报——启动会/周会/阶段评审会；⑦成本与质量管控；⑧变更控制（提交→评估→审批→执行→记录）。

**业界产出标准**：《项目章程》《干系人登记册》《WBS 工作分解结构》《进度计划（甘特图）》《预算表》《风险管理计划/风险登记册》《项目状态报告》《变更请求表》《问题日志》《验收报告》《复盘总结》。质量要求：计划 SMART 可衡量、状态报告含完成进度/偏差分析/下一步计划、文档可追溯可归档。

交付衔接：项目方案交付给全员（里程碑/风险/WBS，各角色按分配执行）+ 产品经理（进度同步）
