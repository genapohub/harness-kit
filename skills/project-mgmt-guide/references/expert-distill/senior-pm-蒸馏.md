## 一、Spec → 任务拆解的核心纪律

1. **引用原文，不加戏**：任务必须引用 spec 原文需求——不添加 spec 里没有的 luxury/premium 功能
2. **多数 spec 比看起来简单**：先按字面拆，别脑补复杂度
3. **现实范围**：基础实现是正常且可接受的；先功能后打磨；首次实现预留 2-3 轮修订
4. **去镀金（No Gold-Plating）**：spec 说"联系表单"就拆"联系表单"，不升级成"带 CRM 集成的智能表单"

## 二、任务清单格式模板（开发者可直接执行）

```markdown
# [项目名] 开发任务清单

## 规格摘要
**原始需求**：[引用 spec 关键需求原文]
**技术栈**：[从 spec 提取，含 CSS 框架/依赖]
**目标周期**：[按范围现实估算]

## 开发任务

### [ ] 任务 N：{功能名}
**描述**：{做什么，一句话，具体不抽象}
**验收标准**：
- {可测试的行为 1（如"页面无报错加载"）}
- {可测试的行为 2（如"规格中的区块全部存在"）}
- {可测试的行为 3}
**涉及文件**：{文件清单}
**参考**：Spec 第 X 节

## 质量要求（Quality Requirements）
- [ ] 所有依赖用支持的 props/API，不发明不存在的
- [ ] 命令不挂后台进程——绝不 append `&`
- [ ] 不包含"启动服务器"命令——假设开发服务已在跑
- [ ] 移动端响应式必须
- [ ] 表单功能必须可用（如 spec 含表单）
- [ ] 图片只用已授权来源，不用会 403 的图源
- [ ] 含截图验证：跑一次 Playwright 截图留证

## 技术备注
**开发栈**：[spec 精确要求] / **特殊指示**：[客户特定请求] / **周期预期**：[按范围现实估算]
```

**任务粒度铁律**：每个任务 = 开发者在 **30-60 分钟**内可实施 + 自带验收标准——超出说明拆得不够细。

## 三、AI 写任务清单的防坑清单（Quality Requirements 背后逻辑）

> 这些坑是 AI 生成任务清单的高发区，AI 常写出"看似完整但跑不动"的任务：

1. **不发明 API**：组件/依赖只用真实存在的 props——AI 常编造不存在的配置项
2. **命令不加 `&` 后台运行**：挂后台 = 没人看得到报错 = 任务"假完成"
3. **不含启动服务器命令**：把"假设环境已就绪"写进任务前提，避免重复起服务
4. **图片来源受限**：只用白名单图源（Unsplash/picsum），不用会 403 的图床
5. **留验证证据**：任务完成标准含自动化截图/测试留证，不靠"我觉得好了"

---

## 四、沟通风格（PM 说人话）

- **具体**："实现含姓名/邮箱/留言字段的联系表单"，不说"加个联系功能"
- **引原文**：参考需求时引用 spec 原文，不转述变形
- **现实**：基础需求不承诺豪华结果
- **开发者优先**：任务拿过来就能动手，不用再猜

## 五、与原生方法论及 mvp-team-lead 蒸馏的配合

| 场景 | 用哪个 |
|------|--------|
| 真人项目立项/迭代/风险 | `项目管理方法论.md`（原生，主） |
| AI 编排型项目 Phase 门禁/Spec 契约 | mvp-team-lead-蒸馏（大湾区靓仔） |
| **把 Spec/需求拆成可直接开发的 30-60 分钟任务清单** | **本文档（增量，唯一来源）** |

> **使用原则**：需求确认后进入拆任务阶段，用本文档模板 + 粒度纪律 + 防坑清单生成开发任务清单——任务可执行、范围不镀金、AI 不会写"跑不动的任务"。
