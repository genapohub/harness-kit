## 一、团队级 P0 绝对规则（跨角色质量红线，三禁）

> 适用于任何成员、任何产出，违反 = 退回重做。用于**AI 编排项目**时尤其重要——这是把 AI 常见"模板味/泛化审美"挡在门外的硬规则。

1. **禁止 emoji 作为功能图标** — 图标必须是统一描边、可矢量缩放、语义明确的 SVG 图标方案；Spec 锁定**一套**图标库全项目统一不混用；尺寸 16px(行内)/20px(按钮)/24px(独立)。emoji 仅允许出现在 UGC 和 IM 消息。
   - 检测正则：`[\x{1F300}-\x{1F9FF}\x{2600}-\x{26FF}\x{2700}-\x{27BF}\x{FE00}-\x{FE0F}...]`（各 Phase 门禁扫描所有产出）
2. **禁止紫色→粉色渐变主视觉** — 禁 `linear-gradient(135deg, #7C3AED→#A855F7→#EC4899)` 及 Indigo→Pink 任意组合；红线禁的是"渐变 + 发光边框 + 毛玻璃"三位一体的 AI 模板套路
3. **禁止 AI 模板味** — 禁 "Lorem ipsum"/"Welcome to Our App" 等空洞占位；禁硬编码颜色值（唯一例外 #fff/#000）；禁弹跳缓动 `cubic-bezier(0.68,-0.55,0.265,1.55)`

**配套**：规则 vs 选型分离——专家团定"规则"（不用 emoji/分层/可回滚等，强制通用），具体技术选型（框架/图标库/平台）由架构师按项目定并锁进 Spec；任何 agent 把"具体技术"写成"必须用 X"即越权。

## 二、6 Phase 门禁治理模型（编排型项目 SOP）

| Phase | 内容 | 门禁（不过不前进） |
|-------|------|-------------------|
| **0 需求澄清** | 一轮提问定调（用户是谁/场景/不做会怎样/参照/技术约束），总结为 3 句话 | 需求确认（唯一交互点） |
| **1 并行调研** | PM 竞品 + 架构师技术 + 设计师设计三方并行，交叉验证一致性 | **用户确认三文档** |
| **1.5 Spec 生成** | 基于确认的 PRD+架构+UIUX 生成规格契约，之后一切以 Spec 为准 | 内部自动 |
| **2 设计细化** | 架构师细化 API/DB，设计师出页面（Spec 页面清单 + Token） | 设计门禁（P0 规则 + 反模式检查） |
| **3 并行开发** | 前端/后端并行，lint→type-check→test 自检最多 3 轮 | 代码组织门禁 + emoji 扫描 |
| **4 测试交付** | QA 先测（P0 归零）→ 运维部署验证 → 交付 | P0 缺陷归零才能部署 |

**编排铁律**：信息必须经总监中转（成员不直连）、每个专家的交付物必须本人输出（不代写不合并）、逐 Phase 推进不跳步、成员结论为准。

## 三、Spec 即契约（范围锁定的核心工具）

> 用户确认三文档后生成，**之后的开发以 Spec 为唯一依据**。Spec 锁定的 13 章节：

```
1. 产品定义（一句话/目标用户/核心问题）
2. MVP 范围（锁定——不在此列表一律不做，含 RICE 评分）
3. 明确不做（Out-of-Scope，每条带原因，防范围蔓延）
4. 技术架构（锁定——框架写实际版本号，防幻觉 API）
5. API 端点清单（锁定 + openapi.yaml）
6. 数据库表清单（锁定）
7. 页面清单（锁定：页面/路由/核心组件/对应 API/Token 主题）
8. 设计 Token（锁定：主色/字体/图标库/主题/对标品牌）
9. 验收标准（锁定——EARS 格式：While/When/If/Where + 系统必须/应该 + 行为）
10. 边界与约束（不支持 IE/断点/性能目标）
11. 内嵌已知坑（从项目 pitfalls 记忆拉取）
12. 端到端验证步骤（一条可执行命令流覆盖成功流+错误流）
13. 变更记录
```

**变更分级**（Spec 一旦确认即锁定，改动走流程）：
- **小改**（不新增 API/DB 表/影响 ≤2 页面/不改核心流程）→ 更新 Spec 变更记录继续
- **大改**（满足任一）→ 回 Phase 0 重新需求澄清 + 更新三文档 + Spec

## 四、冲突解决协议（6 类常见冲突）

| 冲突 | 处理 |
|------|------|
| 架构师说功能不可行 | 区分"完全不可行"还是"成本高"——后者要替代方案，前者反馈 PM 调整 PRD |
| PM 与设计师方向不一致 | 对齐竞品分析与对标品牌，总监裁决 |
| 前端抱怨设计太复杂 | 先让设计师简化（不砍功能），MVP 不可行再裁定降级方案 |
| QA 发现 P0 缺陷 | 打回对应开发修完重测；2 次打回不过 → 总监介入审查（代码问题 or Spec 不清） |
| 用户中途改需求 | 回 Phase 0 重新澄清，小改调整计划，大改重走全流程 |
| 打回-重做超 3 轮 | 升级通知用户或停下（Bounded，防死循环） |

## 五、快速路径裁剪（按项目类型选规模）

| 项目类型 | 判断条件 | 编排规模 |
|----------|----------|----------|
| 轻量级 | 纯静态/单页/无后端 | 只 spawn 设计师 + 前端 |
| 迷你 | 2-3 页 + 云函数 | PM + 设计师 + 前端 + 运维（4 人） |
| 标准 | 需 API + DB + 认证 | 全 8 人 |

> **对单人或小团队编排的意义**：不是所有任务都要全套人马——先判断类型再决定召集哪些角色，省时省 token。

## 六、质量门禁矩阵（每 Phase 谁把关、不过怎样）

| Phase | 门禁 | 执行者 | 不通过后果 |
|-------|------|--------|------------|
| 1 | 用户确认三文档 | 用户 | 不能进 Spec |
| 2 | emoji 扫描 + 反模式检查 | 总监 | 退回设计师 |
| 3 | 代码组织门禁（分层/≤300 行/单一职责）+ emoji 扫描 | 总监+开发 | 退回重做 |
| 4 | P0 缺陷归零 + 最终 P0 全量扫描 | QA | 不能部署 |

## 七、决策与记忆配套

- **决策日志**：`[{时间}] Phase {N} - {决策} - {原因} - {影响}`，每个 Phase 关键决策必记
- **悬而未决登记（OPEN-DECISIONS）**：定不下来/等外部条件 → 立即落条（Date/Source/Open Item/Constraints/Current Leaning/Blocked By/Resolves When/Status），只追加就地关闭，已决可升格 ADR
- **踩坑自学习闭环**：错误归类 → 稳定签名落 `pitfalls.jsonl`（同签名只追加 episode 计数）→ 开发前按技术栈指纹召回（不靠文字匹配）→ 真实通过才标 validated（不认"我觉得修好了"）

## 八、与原生方法论的配合

| 场景 | 用哪个 |
|------|--------|
| 真人项目：立项/迭代/进度/风险 | `项目管理方法论.md`（原生，主） |
| **AI/多角色编排项目：Phase 门禁 / Spec 契约 / 变更分级 / 冲突协议 / P0 三禁** | **本文档（增量）** |

> **使用原则**：项目由 AI 多角色协同（orchestrator 调度/虚拟团队）执行时，用本文档的 Phase 门禁 + Spec 锁定 + 变更分级管住"AI 跑偏"；真人敏捷迭代用原生方法论。
