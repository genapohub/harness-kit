## 一、场景识别

| 场景 | 名称 | 判断条件（满足任一） | 产出量 | 预估周期 |
|------|------|---------------------|--------|---------|
| 场景一 | 0→1 测试体系建设 | 全新项目/团队、无测试基础设施、需从零搭建测试框架与流程 | 10-12类 | 3-6周 |
| 场景二 | 中大型测试需求 | 新增功能模块的全面测试、新增测试类型(如性能/安全)、测试流程优化 | 6-8类 | 1-3周 |
| 场景三 | 单功能测试/Bug验证 | 单个功能的测试用例补充、Bug的回归测试、测试数据准备 | 2-3类 | 1-2天 |
| 场景四 | 大版本测试策略升级 | 测试框架迁移、自动化覆盖率大幅提升、引入新测试类型 | 8-10类 | 2-6周 |
| 场景五 | 测试技术预研 | 新测试工具评估、测试技术方向探索 | 3-4类 | 1-2周 |

### 识别流程

```
是否全新项目/无测试体系？ → 是 → 场景一
    ↓否
是否测试框架迁移/自动化覆盖率大幅提升？ → 是 → 场景四
    ↓否
是否为工具评估/技术方向探索？ → 是 → 场景五
    ↓否
是否涉及多模块/多测试类型/多环境？ → 是 → 场景二
    ↓否
→ 场景三
```

## 二、场景一：0→1 测试体系建设（12类产出）

### 规划阶段
1. **测试需求分析** — 产品质量要求、上线标准、测试范围、历史Bug分析
2. **测试策略文档** — 测试金字塔定义（单元/集成/E2E比例）、测试类型覆盖（功能/性能/安全/兼容/可访问性）、质量门禁标准
3. **测试工具选型** — 单元测试(框架)、API测试(工具)、E2E测试(工具)、性能测试(工具)、测试管理平台、缺陷管理工具

### 实施阶段
4. **单元测试方案** — 测试框架配置、Mock/Stub策略、覆盖率目标（行≥80%/分支≥70%）、测试文件组织规范
5. **集成/API测试方案** — 接口测试框架、测试数据管理、环境隔离策略、契约测试（Consumer-Driven Contract）
6. **E2E测试方案** — 关键用户路径定义、测试环境管理、测试数据工厂、截图/录屏策略、失败重试机制
7. **性能测试方案** — 性能基准定义（QPS/P95延迟/错误率）、压测场景设计（基准/负载/压力/稳定性）、压测工具选型、压测环境要求、性能回归阈值
8. **安全测试方案** — SAST（静态代码扫描）、DAST（动态安全扫描）、依赖漏洞扫描、安全测试Checklist（OWASP Top 10）

### 流程与基础设施
9. **测试环境管理** — 环境拓扑（dev/test/staging/perf）、数据管理（脱敏/刷新/隔离）、环境拉起/销毁自动化、Mock服务
10. **CI/CD测试集成** — Pipeline中测试阶段设计、质量门禁（覆盖率/通过率/安全扫描）、测试报告生成、失败通知
11. **缺陷管理规范** — Bug生命周期（提交→确认→修复→验证→关闭）、优先级/严重性定义、缺陷分析（根因/趋势/模块分布）
12. **质量度量体系** — 测试覆盖率、通过率、缺陷密度、缺陷逃逸率、MTTR/MTTD、质量Dashboard

## 三、场景二：中大型测试需求（6-8类产出）

1. **测试范围与策略** — 功能模块的测试范围、测试类型选择、风险分析
2. **测试用例设计** — 等价类/边界值/场景法/状态迁移、正常+异常+边界全覆盖、测试数据设计
3. **自动化测试方案** — 自动化范围（哪些适合/不适合自动化）、脚本设计模式（Page Object/Screenplay）
4. **性能测试方案** — 关键接口压测、并发用户模拟、性能瓶颈定位
5. **兼容性测试方案** — 浏览器/设备/系统版本矩阵、测试范围优先级
6. **测试报告模板** — 测试结果汇总、缺陷分布、风险评估、上线建议
7. **回归测试策略** — 回归范围选择（全量/部分/风险驱动）、自动化回归
8. **测试数据与环境** — 数据准备方案、环境申请、数据清理

## 四、场景三：单功能测试/Bug验证（2-3类产出）

1. **测试用例** — 功能点拆解、测试步骤、期望结果、测试数据
2. **Bug回归用例** — 修复验证步骤、关联功能回归清单
3. **测试执行记录** — 执行结果、缺陷记录、截图/日志证据

## 五、场景四：大版本测试策略升级（8-10类产出）

1. **现状评估** — 当前测试体系痛点、覆盖率现状、缺陷逃逸分析
2. **目标定义** — 升级后目标（覆盖率/自动化率/测试效率）、成功指标
3. **框架选型与迁移** — 新旧框架对比、迁移策略、并行运行方案
4. **测试用例迁移计划** — 迁移优先级、自动化脚本改造、不适用用例处理
5. **自动化测试框架搭建** — 新框架架构设计、工具链整合、CI集成
6. **性能测试基准更新** — 新基准定义、压力模型更新
7. **测试流程优化** — 测试左移/右移、质量门禁优化、反馈效率提升
8. **团队培训** — 新工具培训、最佳实践分享、FAQ文档
9. **过渡期管理** — 新旧并行运行、质量对比验证
10. **效果评估** — 升级前后关键指标对比

## 七、测试通用规范

### 测试金字塔
```
          ╱  E2E  ╲        10% — 关键用户路径
         ╱  集成/API ╲      30% — 接口/组件/服务间
        ╱   单元测试   ╲     60% — 函数/方法/类
```

### 测试用例编写规范
- 命名：`{被测模块}_{场景}_{预期结果}`
- 结构：前置条件 → 测试步骤 → 预期结果 → 实际结果
- 覆盖：正常路径 + 异常路径 + 边界值 + 权限场景
- 优先级：P0（核心/阻塞）→ P1（重要）→ P2（一般）→ P3（低优）

### Bug 优先级与严重性
| 严重性 | 优先级 | 示例 |
|--------|--------|------|
| 致命 | P0 | 系统崩溃、数据丢失、安全漏洞 |
| 严重 | P1 | 核心功能不可用、数据错误 |
| 一般 | P2 | 非核心功能异常、体验问题 |
| 轻微 | P3 | 文案/UI偏差、优化建议 |

### 性能测试场景模板
| 场景 | 并发 | 持续时间 | 通过标准 |
|------|------|---------|---------|
| 基准测试 | 1 | 5min | P95<目标值 |
| 负载测试 | 预期峰值×1 | 30min | 无错误 |
| 压力测试 | 预期峰值×1.5→2 | 逐步增加 | 找到瓶颈 |
| 稳定性测试 | 预期峰值×0.8 | 4-8h | 无内存泄漏/错误率恒定 |
| 尖峰测试 | 短时×3 | 5min×3轮 | 自动恢复 |

---

### 测试用例模板（可填空）

| 字段 | 内容 |
|------|------|
| 用例编号 | {模块缩写}-{序号}，如 ORDER-001 |

## 八、下游交付衔接

> 测试报告不是终点——Bug 要开发修、上线要 PM 拍板、门禁要 DevOps 配置。明确「给谁用、对方要什么」，质量信息才能真正流动。

### 8.1 下游角色与交付矩阵

| 下游角色 | 交付物 | 对方需要的核心信息 | 常见退货原因 |
|---------|--------|------------------|-------------|
| 开发工程师 | Bug 报告、回归验证结果 | 复现步骤（环境/版本/步骤/期望vs实际）、根因线索（日志/截图/怀疑点）、严重性定级 | Bug 只写"点击报错"没有环境与版本；无法复现 |
| 项目经理 | 测试报告、上线建议 | 通过率/遗留 Bug 清单（分级/责任人）、上线风险、Go/No-Go 结论 | 只有数字没有结论——PM 不知道能不能上 |
| 产品经理 | 质量验收报告 | 需求覆盖对照（PRD 逐条 vs 测试结果）、体验类问题清单 | 测了 500 条用例但和 PRD 对不上号 |
| DevOps | 质量门禁规则 | 覆盖率阈值、通过率阈值、阻断条件、性能回归阈值 | 阈值没有依据，设太严全阻断、设太松等于没有 |

### 8.2 交付动作三步

1. **交前核对**：Bug 报告可复现（他人按步骤能重现）、测试报告有明确结论（不是"基本通过"）、遗留 Bug 有分级与责任人三件齐全。
2. **交底说明**：向 PM 汇报用「结论先行」——先说 Go/No-Go，再说理由；遗留 P1/P2 Bug 逐条给出"带病上线的影响面"。
3. **交后跟进**：上线后 48h 内跟踪生产监控与客诉，验证"带病上线"的判断是否成立——这是测试闭环，也是下版本回归输入。

### 8.3 上游输入依赖

| 上游角色 | 需要的输入 | 缺失时的降级策略 |
|---------|-----------|-----------------|
| 产品经理 | PRD（含验收标准）、需求变更记录 | 按"探索性测试"模式覆盖，并在报告中标注"验收标准缺失，覆盖完整性未知" |
| 开发工程师 | 提测说明（改动点/影响面/自测范围） | 按全量回归准备，工作量翻倍需提前告知 PM |
| DevOps | 测试环境可用性、造数工具 | 用 Mock + 数据工厂兜底，但需在报告中声明环境限制 |

### 8.4 交付物命名与归档

- 测试报告：`{项目名}_{版本}_测试报告_v{序号}.md`，归档至项目知识库供下版本回归参考
- Bug 单：标题含模块+现象（`[支付] 重复点击导致双扣款`），便于统计模块缺陷密度

## 九、AI 工具使用建议

| 阶段 | AI 用途 | 注意事项 |
|------|---------|---------|
| 用例设计 | 生成测试用例初稿（等价类/边界值） | AI 产物偏教科书——必须人工补"只有踩过坑才知道"的边界场景 |
| Bug 分析 | 日志解读、根因假设生成 | 复现步骤必须人工验证，AI 的根因只是假设 |
| 自动化脚本 | 脚本骨架/Page Object 生成 | 元素定位与等待策略需按真实页面调整，AI 看不到实际 DOM |
| 测试数据 | 批量造数脚本 | 手机号/身份证等敏感字段必须脱敏，遵守数据合规 |
| 测试报告 | 结果汇总初稿 | Go/No-Go 结论必须 QA 签字——AI 不承担质量责任 |

**红线**：上线建议的最终判断、带病上线的风险签字——不允许 AI 代做。AI 生成的用例如果没有人工补充的"真实世界边界场景"（弱网/切后台/并发点击/时区跨天），覆盖率数字再高也是假安全感。

## 十、产出质量检查清单

### 10.0 验证铁律（Iron Law · 吸收 superpowers verification-before-completion · 2026-09）

> **声称完成/通过之前，必须贴出本轮跑过的验证输出。** 没有新鲜验证证据的完成声明 = 撒谎。

- ❌ "测试应该能过" / "代码看着没问题" / "上次跑过通过了"
- ✅ "`pytest tests/test_order.py -v` → 12 passed, 0 failed（本轮输出附后）"
- ✅ "压测结果：P95=612ms < 800ms 阈值，错误率 0.02%（本轮压测报告附后）"

**验证门禁**：
1. 声明"通过"前，确认验证命令在本轮（本会话）实际执行过
2. 输出必须贴出关键证据（命令 + 结果摘要），不是口头保证
3. 回归结论必须基于本轮运行，不能引用"上轮跑过"

- [ ] 测试策略覆盖金字塔三层（单元/集成/E2E）
- [ ] 测试类型覆盖充分（功能/性能/安全/兼容性）
- [ ] 测试用例含正常+异常+边界+权限场景
- [ ] 覆盖率目标明确（行/分支/函数）
- [ ] 性能测试含基准+负载+压力+稳定性
- [ ] CI/CD 集成质量门禁（覆盖率/通过率/安全扫描）
- [ ] 缺陷管理规范完整（生命周期/优先级/根因分析）
- [ ] 测试环境可独立拉起/销毁
- [ ] 质量 Dashboard 覆盖核心指标
- [ ] 测试数据脱敏、可刷新

### 去AI味检查
- [ ] 测试用例中有至少 3 个"只有踩过坑才知道要测"的边界场景
- [ ] 自动化测试策略不是"越多越好"——说明了哪些不适合自动化的场景及理由
- [ ] 性能测试的通过标准有具体的 P95/P99 数值
- [ ] Bug 报告不只有步骤和截图——有"为什么我怀疑是这个原因"的分析

## 十一、超越AI味：测试工程师的真实直觉

> AI 能生成 100 个测试用例，但真正的QA知道——Bug 从来不躲在教科书里的等价类和边界值。

### 11.1 反AI测试决策五条

**1. 测试用例要有"猎手直觉"**

- 错误做法: 等价类+边界值+判定表（教科书三件套）
- 正确做法: "用户可能在支付时切出去回微信，回来时支付状态可能不一致——加一个切后台->回前台->重查支付状态的用例"

**2. 自动化不是越多越好**

- "核心支付链路自动化（因为不能挂），UI 动画效果手动测（因为自动化脚本维护成本>收益），一次性活动页面不用自动化"

**3. 重现 Bug 比报告 Bug 更重要**

- 错误做法: "步骤：1. 打开页面 -> 2. 点击按钮 -> 3. 观察到报错"
- 正确做法: "步骤：1. 用 iOS 16 的 Safari -> 2. 先登录再退登 -> 3. 不清缓存直接重新登录 -> 4. 点击支付 -> 5. 报 401。怀疑是登出时 token 没清干净"

**4. 性能测试要有"用户视角"的通过标准**

- "P50 < 200ms / P95 < 800ms / P99 < 2s / 错误率 < 0.1%。超过 P99 阈值的请求视为不可接受"

**5. 安全测试要有"攻击者思维"**

- "普通用户A能不能通过改 URL 参数看到用户B的订单？未登录能不能直接调 API？上传文件能不能传 .php 后缀？"

### 11.2 QA 直觉：哪里最容易出 Bug

| 高风险区域 | 为什么 | 测试策略 |
|-----------|--------|---------|
| 时间相关逻辑 | 时区/夏令时/跨天/月末 | 改系统时间测试 + 模拟跨时区 |
| 并发/竞态 | 点击太快/网络慢/切后台 | 连点器测试 + 弱网模拟 |
| 第三方依赖 | SDK版本变更/接口限流/降级 | Mock 异常返回 + 超时测试 |
| 数据迁移 | 字段类型变更/历史脏数据 | 用生产脱敏数据跑迁移脚本 |
| 权限边界 | 越权比功能Bug更致命 | 横向越权 + 纵向越权 |

### 11.3 反合理化 Red Flags：跳过流程的借口（吸收 superpowers · 2026-09）

> 这些念头一出现就是 STOP 信号——你在为跳过测试流程找借口。真实 QA 的经验是：**越简单的改动越容易翻车，因为它默认不会被测。**

| 念头 | 现实 |
|------|------|
| "这个改动就一行，不用走流程" | 一行改动也可能牵动状态机/缓存/权限。走流程 ≠ 出大文档，可能是两条测试用例 |
| "手动测过了，不用写用例" | 手动测试无记录、不可复跑、覆盖不全。用例是留档，不是仪式 |
| "先上线，Bug 后面再补测" | 上线后补的用例第一次就跑过——从没看过它失败，证明不了它能抓 Bug |
| "性能现在没空测，先上线" | 没定 P95/P99 阈值的上线就是裸奔。压测半小时，返工按天算 |
| "这个场景教科书里没有" | 教科书没有 = 真实世界里全是。切后台/弱网/时区跨天才是 Bug 老巢 |
| "回归全跑太慢，挑几条吧" | 挑着跑 = 给漏测留了后门。核心链路一条都不能少 |

### 交付物去AI味自检（强制）

> **规则：每份对外交付的文档末尾，必须附「去AI味自检」段，至少 3 条**，从以下维度自检，缺一即视为交付不完整：

| 维度 | 自检问题 | AI 味反例 |
|------|---------|----------|
| 不做决策 | 是否明确说了「不做什么」？ | 只列功能清单，无取舍 |
| 数字具体 | 目标/指标/约束是否具体到数字？ | 「提升体验」「提高转化率」 |
| 竞品立场 | 与竞品的差异是否有一句话立场？ | 「借鉴头部最佳实践」 |
| 此刻合理性 | 为什么现在做？不做会怎样？ | 不解释时机 |
| 优先级倾斜 | P0/P1 是否有倾斜逻辑？ | 全功能同等权重 |

**自检段格式**（置于文档末尾）：

```markdown
## 去AI味自检
- ✅ 不做决策：...
- ✅ 数字具体：...
- ✅ 竞品立场：...
- ✅ 此刻合理性：...
- ✅ 优先级倾斜：...
```
