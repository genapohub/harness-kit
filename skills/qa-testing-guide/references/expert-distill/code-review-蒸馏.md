## 一、评审五维焦点（不评风格，评实质）

1. **正确性** — 它做的是该做的吗？
2. **安全** — 有漏洞吗？输入校验？鉴权检查？
3. **可维护性** — 6 个月后还有人看得懂吗？
4. **性能** — 有明显瓶颈或 N+1 查询吗？
5. **测试** — 重要路径被测试覆盖了吗？

> 评审的"第一性原理"：**正确性 > 安全 > 可维护 > 性能 > 测试**，优先级从高到低；tabs vs spaces 不评（交给 linter）。

---

## 二、三级问题分级（每条评论必须带标记）

| 级别 | 标记 | 含义 | 必须修? |
|------|:---:|------|:---:|
| **Blocker** | 🔴 | 安全漏洞（注入/XSS/越权）、数据丢失风险、竞态/死锁、破坏 API 契约、关键路径缺错误处理 | ✅ 必修 |
| **Suggestion** | 🟡 | 缺输入校验、命名混乱、重要行为缺测试、N+1/不必要分配、可抽取的重复代码 | ⚠️ 应修 |
| **Nit** | 💭 | 风格不一致（无 linter 管）、小命名优化、文档缺口、值得考虑的替代方案 | 可选 |

---

## 三、评审评论格式（每条含 3 要素）

```
🔴 **Security: SQL Injection Risk**
Line 42: 用户输入被直接插进查询。

**Why:** 攻击者可将 `'; DROP TABLE users; --` 注入为 name 参数。

**Suggestion:**
- 用参数化查询：db.query('SELECT * FROM users WHERE name = $1', [name])
```

**三要素**：①具体位置（文件:行）+ 问题描述 ②为什么是问题（攻击场景/后果）③可操作建议（怎么做）。缺一不算合格评论。

---

## 四、评审沟通六原则（当导师，不当门卫）

1. **具体**："42 行可能造成 SQL 注入"，不说"有安全问题"
2. **解释为什么**：不只说改什么，说清理由
3. **建议非命令**："考虑用 X 因为 Y"，不说"改成 X"
4. **优先级标记**：每条评论带 🔴/🟡/💭
5. **表扬好代码**：指出聪明的解法和干净的模式（正面反馈是评审的润滑剂）
6. **一次评审给全**：不挤牙膏式跨轮次补评论（先整体总结 → 逐条 → 鼓励收尾）
