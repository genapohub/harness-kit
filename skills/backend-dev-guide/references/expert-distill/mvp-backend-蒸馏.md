## 一、文件组织硬规则（违反即不合格，可脚本门禁）

| 规则 | 要求 |
|------|------|
| 单一职责 | 一个文件一个主职责、一个主导出 |
| **单文件 ≤ 300 行** | 超限必须按子功能拆文件 |
| 按资源分包 | 一个资源 = controller + service + repository 三件套 |
| 入口只装配 | `app.ts`/`main.py` 只挂中间件+路由+启动，**零业务逻辑** |
| 逻辑下沉 | 业务逻辑进 service，不进路由处理器、不进 utils |
| 类型/Schema 独立 | 请求校验、类型定义单独成文件 |

**分层依赖铁律**（只能向下）：
```
Routes/Controllers（校验→调 service→组装响应）
  ↓ Services（业务逻辑、事务编排）
  ↓ Repositories（数据访问）
  ↓ 基础设施（DB/Redis/第三方）
```
- Controller **禁止**直连数据库；Service **禁止** import `req`/`res`；Repository **禁止**含业务逻辑

**门禁命令**（CI 或 review 直接跑）：
```bash
find src -name '*.ts' | xargs wc -l | awk '$1>300{print "OVER:",$0}'
```
任何文件超 300 行或入口含业务 → 退回重做。

## 二、每端点实现 checklist（五件套齐了才算完成）

1. **参数校验**：Zod/Pydantic schema，白名单验证（先于一切业务）
2. **业务逻辑**：调 service 层，不在路由里写
3. **错误处理**：统一响应 `{ code, data, message }`，按错误分层（见下）
4. **请求日志**：logger.error 带 userId + error（不暴露堆栈给客户端）
5. **安全自检**：
   - 认证：JWT Bearer，15min access + 7d refresh
   - 授权：检查用户是否有权操作该资源（不是自己的数据不能改）
   - 输入校验：服务端必校验，不只依赖前端
   - 速率限制：敏感端点（登录/注册/支付）≥ 10 次/分钟
   - SQL 注入防护：ORM 参数化查询，禁原始 SQL 拼接

**错误处理三层**：参数校验 → 400；业务规则冲突（库存不足/权限不够）→ 409/403；全局兜底 → 500（记日志，不暴露细节）。

## 三、缓存键设计表（Redis 落地参考）

| 场景 | 缓存键格式 | TTL | 说明 |
|------|-----------|-----|------|
| 用户会话 | `session:{user_id}` | 7 天 | JWT Refresh Token 存储 |
| 热点数据 | `cache:{endpoint}:{params_hash}` | 5-60 分钟 | 列表/详情接口缓存 |
| 限流计数 | `rate_limit:{ip}:{endpoint}` | 1 分钟 | 滑动窗口限流 |
| Feature Flag | `flag:{key}` | 5 分钟 | 灰度标记 |

**缓存纪律**：写操作后删相关键（SCAN + DEL）；TTL 必须有值，禁止永不过期；先量后缓（无数据证明热点不加缓存）。

## 四、失效模式自检清单（6 类 · AI 生成代码交付前必过）

> AI 写的代码最容易在这 6 处静默出错——交付前逐项核对，比跑测试更重要。

| # | 失效模式 | 检查方法 |
|---|----------|----------|
| 1 | Happy-path 偏差 | 错误/边界/超时分支是否齐全？（AI 只写主流程是通病） |
| 2 | **沉默逻辑错误（最致命）** | 未测试覆盖的行为是否悄悄算错？——货币计算/权限取反/数据一致性/事务隔离 |
| 3 | 幻觉依赖/接口 | 新增依赖真实存在？API 签名对照真实文档？（AI 编造库名/签名） |
| 4 | 缺失系统上下文 | 权限/限额/网络策略/多租户隔离是否逐项验收？ |
| 5 | 性能盲区 | N+1 查询/循环内 IO/无分页/无索引/无超时？ |
| 6 | 静默缺失 | 漏 import/未处理 Promise/未 close 连接？ |

## 五、性能目标基线（MVP 后端）

| 指标 | 目标 | 测量方式 |
|------|------|----------|
| API 响应时间 | p95 < 500ms | 服务端中间件计时 |
| 数据库查询 | 单次 < 50ms | ORM 日志 |
| 并发支持 | 100 req/s 不崩溃 | k6 / wrk |
| 错误率 | < 1% | 日志聚合 |

**查询优化**：高频字段加索引（MVP 不建复合索引，等慢再加）；避免 N+1（include/select 一次加载关联）；列表默认分页。

**数据库迁移**：迁移文件进版本控制；每份迁移可回滚（down migration）；上线前先在 staging 跑一遍。
